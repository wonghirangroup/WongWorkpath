# Software Requirements Specification (SRS)

เอกสารนี้สรุปข้อกำหนดความต้องการของระบบ Wong Workpath โดยดึงมาจากพฤติกรรมจริงของโค้ดที่ใช้งานอยู่ ไม่ใช่ข้อกำหนดที่เขียนไว้ล่วงหน้าก่อนพัฒนา (retro-documented)

## 1. ขอบเขตระบบ (Scope)

ระบบจัดการงานภายในบริษัทแบบครบวงจร ครอบคลุมโครงการ งาน นัดประชุม เอกสาร รหัสผ่าน และบัญชีพนักงาน ใช้งานผ่านเว็บเบราว์เซอร์เท่านั้น ไม่มีแอปมือถือแยก

## 2. ผู้ใช้งานระบบ (Actors)

| Actor | คำอธิบาย |
|---|---|
| พนักงานทั่วไป (employee) | ผู้ใช้งานส่วนใหญ่ของระบบ |
| Admin | ดูแลบัญชีพนักงานระดับล่าง |
| Super Admin | ผู้ดูแลระบบสูงสุด (มีได้ 1 คน) |
| ผู้บริหาร (executive) | เห็นภาพรวมทั้งบริษัท (มีได้ไม่เกิน 2 คน) |

## 3. ความต้องการเชิงฟังก์ชัน (Functional Requirements)

### 3.1 การยืนยันตัวตน (Authentication)
- FR-1.1: ผู้ใช้ต้องล็อกอินด้วย username/password ก่อนใช้งานทุกฟังก์ชัน ยกเว้นหน้า login และ flow ลืมรหัสผ่าน
- FR-1.2: ระบบต้องล็อกอินผิดเกิน 5 ครั้ง/15 นาที (ต่อ IP+username) หรือ 30 ครั้ง/15 นาที (รวมต่อ IP) แล้วปฏิเสธชั่วคราว (HTTP 429)
- FR-1.3: ผู้ใช้ต้องขอรีเซ็ตรหัสผ่านผ่าน OTP ที่ส่งทางอีเมลได้ (ต้องมีอีเมลผูกกับบัญชี)
- FR-1.4: session ต้องมีอายุ 30 วัน หมดอายุแล้วต้องเด้งกลับหน้า login พร้อมข้อความแจ้ง

### 3.2 การจัดการโครงการ
- FR-2.1: ผู้ใช้ทุกระดับต้องสร้างโครงการใหม่ได้ (ระบุชื่อ ประเภท ตัวย่อ เป็นอย่างน้อย)
- FR-2.2: ระบบต้องออกรหัสโครงการอัตโนมัติ รูปแบบ `{ตัวย่อ}-{ปี พ.ศ. 2 หลัก}-{ประเภท}-{ลำดับ 3 หลัก}`
- FR-2.3: การแก้ไขโครงการที่มีเจ้าของแล้ว ต้องอนุญาตเฉพาะเจ้าของหรือผู้บริหาร คนอื่นต้องยื่นคำขอแก้ไขให้อนุมัติ
- FR-2.4: การลบโครงการต้องจำกัดเฉพาะ Admin ขึ้นไป และต้องลบงาน เอกสาร คำขอที่เกี่ยวข้องตามไปด้วย (cascade) ส่วนรหัสผ่านที่ผูกไว้ต้องย้ายกลับเป็นของส่วนตัวผู้สร้าง ไม่ใช่ลบทิ้ง
- FR-2.5: การสร้างโฟลเดอร์เอกสารพร้อมโครงการต้องเป็นธุรกรรมเดียวกัน (ถ้าอย่างใดอย่างหนึ่งล้มเหลว ต้องไม่มีอะไรถูกสร้างเลย)

### 3.3 การจัดการงาน
- FR-3.1: งานหนึ่งต้องอยู่ในโครงการเดียวเสมอ และเลือกได้ว่าเป็นงานหลักหรืองานย่อย (ผูกกับงานหลัก)
- FR-3.2: สถานะงานต้องคำนวณอัตโนมัติบางส่วน: ไม่มีผู้รับผิดชอบ = ยังไม่เริ่ม, มีผู้รับผิดชอบ = กำลังทำ, งานที่มีงานย่อยสถานะต้องคำนวณจากงานย่อยทั้งหมด (เสร็จเมื่องานย่อยเสร็จครบ)
- FR-3.3: ผู้รับผิดชอบต้องส่งงานได้เมื่อสถานะเป็นยังไม่เริ่ม/กำลังทำ/ติดปัญหา และต้องเลือกผู้ตรวจอย่างน้อย 1 คน
- FR-3.4: ผู้ตรวจต้องตัดสินผลได้ 2 แบบ: ผ่าน (สถานะเป็นเสร็จแล้ว) หรือ ตีกลับ (สถานะกลับเป็นกำลังทำ ต้องระบุเหตุผล)
- FR-3.5: การแก้ไข/ลบงานที่มีผู้รับผิดชอบแล้วต้องผ่านการอนุมัติเช่นเดียวกับโครงการ ยกเว้นงานย่อยที่ไม่ต้องขออนุมัติ

### 3.4 นัดประชุมและปฏิทิน
- FR-4.1: ผู้ใช้ทุกคนต้องสร้างนัดประชุมได้ ผูกหรือไม่ผูกกับโครงการ/งานก็ได้
- FR-4.2: ปฏิทินต้องกรองแสดงผลได้อย่างน้อย 4 แบบ: ทั้งหมด/เฉพาะงาน/เฉพาะนัดประชุม/เฉพาะโครงการ และสลับมุมมอง "ของฉัน"/"ทั้งบริษัท" ได้
- FR-4.3: การยกเลิกนัดประชุมต้องเป็นการเปลี่ยนสถานะ ไม่ใช่การลบทิ้งถาวร (ยกเว้นผู้สร้างนัดหรือ Admin ขึ้นไปที่ลบทิ้งถาวรได้)

### 3.5 เอกสาร (Drive)
- FR-5.1: เอกสารต้องมี 3 ประเภท: โฟลเดอร์ ไฟล์ ลิงก์ และจัดเรียงเป็นโครงสร้างต้นไม้ (parent/child) ได้
- FR-5.2: เอกสารขอบเขตส่วนตัวต้องเห็นได้เฉพาะผู้สร้าง เอกสารขอบเขตโครงการต้องเห็นได้เฉพาะเจ้าของ/สมาชิกโครงการนั้น (ยกเว้นผู้บริหารเห็นทุกโครงการ)

### 3.6 คลังรหัสผ่าน
- FR-6.1: รหัสผ่านต้องมี 3 ขอบเขต: ส่วนตัว (เห็นเฉพาะผู้สร้าง), ทีม (เห็นเฉพาะแผนกเดียวกัน), โครงการ (เห็นเฉพาะคนในโครงการ)
- FR-6.2: ไม่ต้องมีการยืนยันตัวตนชั้นที่สอง (PIN) — การล็อกอินหลักคือขอบเขตความปลอดภัยเดียว (ตัดสินใจแล้วโดยทีม)

### 3.7 การจัดการพนักงานและองค์กร
- FR-7.1: ระบบต้องจำกัดจำนวน Super Admin ไว้ที่ 1 คนเสมอ (ตั้งคนใหม่ = ลดคนเดิมอัตโนมัติ)
- FR-7.2: ระบบต้องจำกัดจำนวนผู้บริหารไว้ไม่เกิน 2 คน และปฏิเสธการตั้งคนที่ 3
- FR-7.3: Admin ทั่วไปต้องกำหนดระดับบัญชีให้คนอื่นได้แค่ระดับ "พนักงาน" เท่านั้น
- FR-7.4: การเปลี่ยนชื่อ-ชื่อเล่นของตัวเอง (พนักงานทั่วไป) ต้องผ่านการอนุมัติจาก Admin ขึ้นไป
- FR-7.5: การเปลี่ยนชื่อฝ่าย/แผนกต้องปรับปรุงข้อมูลพนักงาน/โครงการ/นัดประชุม/คลังรหัสผ่านทีมที่อ้างอิงชื่อเดิมโดยอัตโนมัติในธุรกรรมเดียว

### 3.8 การแจ้งเตือน
- FR-8.1: ผู้ใช้ต้องตั้งช่วงเวลาที่ต้องการให้เตือนก่อนกำหนดส่งงาน/สิ้นสุดโครงการได้เอง เป็นรายบุคคลต่อรายการ (ไม่ใช่ค่ากลางของทั้งระบบ)
- FR-8.2: ช่วงเวลาที่ตั้งได้ต้องไม่เกินความยาวช่วงวันที่จริงของงาน/โครงการนั้น
- FR-8.3: งานที่เลยกำหนดส่งต้องแจ้งเตือนผู้รับผิดชอบหนึ่งครั้งเสมอ ไม่ขึ้นกับการตั้งค่า

### 3.9 บันทึกกิจกรรม (Audit Log)
- FR-9.1: ระบบต้องบันทึกการกระทำสำคัญ (สร้าง/แก้ไข/ลบโครงการ, เอกสาร, พนักงาน, ล็อกอิน/ออกจากระบบ, โครงสร้างองค์กร, คำขออนุมัติ) พร้อมชื่อ ตำแหน่ง แผนกของผู้ทำรายการ ณ เวลานั้น
- FR-9.2: ชื่อผู้ทำรายการในบันทึกต้องมาจากบัญชีที่ล็อกอินจริงเสมอ ห้ามรับค่าจากฝั่งไคลเอ็นต์โดยตรง

## 4. ความต้องการเชิงไม่ใช่ฟังก์ชัน (Non-Functional Requirements)

| หมวด | ข้อกำหนด |
|---|---|
| ความปลอดภัย | ทุก endpoint ต้องผ่านการยืนยันตัวตนด้วย token ยกเว้นหน้า login/ลืมรหัสผ่าน/health check ตัวตนที่แท้จริงต้องมาจาก token ไม่ใช่ค่าที่ client ส่งมา |
| ความปลอดภัยของรหัสผ่าน | รหัสผ่านผู้ใช้ต้องเก็บแบบ hash (bcrypt) ห้ามเก็บ plaintext |
| ความพร้อมใช้งาน | ระบบ production (Render แพลนฟรี) จะ "หลับ" เมื่อไม่มีคนใช้นาน ต้องใช้เวลาปลุกตัว 30-60 วินาทีในการเรียกครั้งแรก — เป็นข้อจำกัดที่ยอมรับแล้ว |
| ความสอดคล้องของข้อมูล | การลบ/แก้ไขที่กระทบหลายตารางต้องทำในธุรกรรมเดียว (transaction) ไม่ปล่อยข้อมูลค้างครึ่งๆ กลางๆ |
| ความเข้าถึงได้ (Accessibility) | สีข้อความ/ไอคอนบนพื้นอ่อนต้องผ่านเกณฑ์ contrast อย่างน้อย 4.5:1 (ตรวจด้วย axe-core, ยกเว้นสีแบรนด์ที่รอการตัดสินใจ) |
| ความสามารถในการบำรุงรักษา | ทุกการแก้ไขโค้ดต้องผ่าน `tsc --noEmit` โดยไม่มี error ก่อน commit |
| การปรับตัวรองรับผู้ใช้พร้อมกัน | ต้องรองรับการทำงานพร้อมกันของพนักงานทั้งบริษัท (ปัจจุบัน ~10 คน) โดยไม่มี race condition ที่ทำให้ข้อมูลเสียหาย (เช่น รหัสโครงการซ้ำ) |

## 5. ข้อจำกัดและสมมติฐาน (Constraints & Assumptions)

- เครื่องพัฒนาทุกเครื่องต่อฐานข้อมูลจริงเดียวกับ production — การทดสอบ/migration บนเครื่องพัฒนามีผลกระทบต่อข้อมูลจริงเสมอ
- ไม่มีการเข้ารหัสข้อมูลระดับแอปพลิเคชัน (encryption at rest) นอกเหนือจากที่ MySQL/โฮสติ้งจัดให้เอง
- ความสัมพันธ์แบบ "หลายต่อหลาย" หลายจุด (เช่น ผู้รับผิดชอบโครงการ/งาน) เก็บเป็นรายการ id ในคอลัมน์เดียว (JSON string) ไม่ใช่ตารางกลางมาตรฐาน จึงไม่มีการบังคับความถูกต้องเชิงอ้างอิง (referential integrity) ระดับฐานข้อมูลสำหรับความสัมพันธ์เหล่านี้ — โค้ดฝั่งแอปต้องกรอง id ที่ไม่มีตัวตนจริงออกเองทุกครั้งที่ใช้งาน
